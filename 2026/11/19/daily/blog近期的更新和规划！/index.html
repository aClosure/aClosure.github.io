PART1-linux运维

按今天实际用到的顺序整理。每条记住“它回答什么问题”就够了，语法可以随时查。

1. 连接与传输

命令 干什么
ssh -i 私钥 user@ip 登录服务器
scp -i 私钥 -r 本地路径 user@ip:/远端路径/ 传文件（-r 表示目录）
exit 或 Ctrl+D 退出 SSH

2. 身份与权限

命令 干什么
whoami 我是谁
id 我的 uid、gid、所属组
sudo -l 我能用 sudo 做什么
sudo 命令 以 root 身份执行一次
chown 用户:组 路径 改所有者
chmod 755 路径 改权限（7=rwx，5=r-x）
ls -ld 目录 只看目录本身的属主和权限

3. 文件与目录

命令 干什么
pwd 我在哪
ls -la 列出全部（含隐藏文件、详情）
cd 路径 切换目录
mkdir -p a/b/c 递归建目录（父目录不存在也能建）
cp 源 目标 / mv 源 目标 复制 / 移动（改名也用 mv）
rm -r 目录 删除目录（慎用，没有回收站）
cat 文件 一次吐出全部内容
less 文件 分页查看，q 退出，/词 搜索
tail -n 50 文件 最后 50 行
tail -f 文件 实时跟随，Ctrl+C 退出
echo '内容' > 文件 写入文件（> 覆盖，>> 追加）
nano 文件 编辑，Ctrl+O 存，Ctrl+X 退

4. 服务管理（systemd）

命令 干什么
systemctl status 服务 在跑吗、最近日志
systemctl start/stop 服务 启 / 停
systemctl restart 服务 重启（断连接）
systemctl reload 服务 重载配置（不断连接）
systemctl enable 服务 开机自启
journalctl -u 服务 -f 实时看该服务日志

5. 网络与端口

命令 干什么
ss -tlnp 谁在监听哪些端口
curl -I http://地址 只看响应头（状态码）
curl http://地址 看响应体
ssh-keyscan -H ip 取服务器主机指纹

6. 磁盘与资源

命令 干什么
df -h 磁盘用了多少
free -h 内存用了多少
top 进程和负载，q 退出
nproc CPU 核数

7. 软件包（Ubuntu/Debian）

事实上笔者用的还是ubuntu（）

命令 干什么
sudo apt update 更新软件索引
sudo apt install -y 包名 安装
sudo apt remove 包名 卸载
apt list --installed | grep 词 查装没装

8. 文本搜索

命令 干什么
grep 关键词 文件 在文件里找
grep -r 关键词 目录 递归找
grep -i 忽略大小写
grep -v 反选（不包含的行）

9. 今天专用的 nginx

命令 干什么
nginx -t 检查配置语法，改完必跑
systemctl reload nginx 让配置生效
tail -f /var/log/nginx/access.log 访问日志
tail -f /var/log/nginx/error.log 错误日志

PART2-操作流程（应该可以这么叫？

今天真正建立起来的，是一条从“连不上服务器”到“push 就发布”的完整链路，以及对每一层失败怎么定位的判断力。命令两周就会忘，这个结构不会。

一、SSH 连接层

  • 密钥登录由三部分组成：本地私钥、服务器 authorized_keys 里的公钥、known_hosts 里的主机指纹
  • Permission denied (publickey) 不区分“用户不存在”和“密钥不对”，这是刻意的安全设计
  • Windows 上私钥权限必须只给自己，否则 OpenSSH 会直接忽略这个文件

二、服务器权限层

  • /var/www 的所有者是 root，普通用户写不进去；要用 sudo 建目录，再用 chown 把目录交给当前用户
  • 改完所有者后，往目录里放文件不用 sudo；但改 /etc/nginx 仍然要
  • reload 不会断开已有连接，restart 会断；改配置优先用 reload

三、nginx 托管层

  • 一个 server 块就是一个站点：监听端口、域名、根目录
  • 静态站就是“nginx 读一个目录”，没有后端进程参与
  • 站点不工作时先查两处：nginx -t 语法、error.log 日志

四、部署层

  • 部署传的是产物（public/），不是源码
  • 构建放在本地或 CI，服务器只负责托管
  • scp 是覆盖，不是同步：删掉的文章不会从服务器上消失
  • 脚本的价值在于把“构建 + 上传”固化成一步，而且任何一步失败就停

五、Git 与 CI 层

  • 主题目录自带 .git 时会被当成子模块，主仓库只存一个指针，于是 CI 检出后主题是空的
  • git rm --cached 只动索引，不删本地文件
  • CI 的每台机器都是全新的，所以每一步都要从零准备（拉代码、装 Node、放私钥）
  • Secret 是交给 CI 的凭据，应该用专用密钥，而不是个人私钥

六、安全层

  • fail2ban 是读日志、按失败次数封 IP，不是限流，也不是 WAF
  • 纵深防御的思路：先关密码登录，再用密钥登录，最后让 fail2ban 盯 SSH

今天踩过的坑（这些比命令更值得记住）

现象 根因
Bad permissions Windows 私钥 ACL 继承了父目录权限
mkdir: Permission denied 父目录属主是 root
页面样式全丢 _config.yml 的 url 没改
CI 报 unknown block tag 主题被当成子模块，没真正进仓库
tail -f 不退出 -f 就是持续跟随，要 Ctrl+C

最后一句

这里可以总结出标准的运维路径：能连上 → 能加固 → 能跑服务 → 能部署 → 能自动化。

以后遇到“某个东西不工作”，先问自己一句话：它卡在哪一层——网络、认证、权限、服务、配置，还是构建？ 能回答这个问题，你就不是在瞎试。
